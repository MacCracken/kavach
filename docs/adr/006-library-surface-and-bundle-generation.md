# ADR-006 — Library surface via `[lib]` + `cyrius distlib`

**Status**: Accepted
**Date**: 2026-07-02
**Version**: v3.6.0

## Context

kavach was scaffolded and has always shipped as a **program** — a
`[build]` entry at `src/main.cyr` that carries its own `main()`, an
end-to-end demo, and a top-level `syscall(SYS_EXIT)`, pulling the 41
domain `src/*.cyr` modules via relative includes. CLAUDE.md anticipated
this: *"a `[lib]` profile may earn a slot when a consumer starts
embedding kavach at the source level."*

That consumer arrived: **mehman**'s M1 sandbox host
(`mehman_sandbox_run_guest`) is designed directly against kavach's
surface (`kavach_init` → `config_new` → `config_backend(PROCESS)` →
`sandbox_create` → `sandbox_transition(RUNNING)` → `sandbox_exec` →
`sandbox_destroy`) and needs to depend on kavach as a Cyrius library.

The first-party Cyrius tree already has a **standard way** to ship a
library: a `[lib]` section listing the domain modules, `cyrius distlib`
to generate a committed single-file `dist/<name>.cyr` bundle + a
`dist/<name>.deps` stdlib sidecar, and `[deps.<name>] modules =
["dist/<name>.cyr"]` on the consumer side, which `cyrius deps`
materializes into the consumer's `lib/<name>.cyr` for source-include.
sigil, patra, and bhumi all ship exactly this way. kavach simply had not
adopted it — it had no `[lib]` section and no `dist/` bundle.

> **Correction note.** An earlier draft of this ADR (and the initial
> v3.6.0 tooling) claimed `cyrius distlib` had been *retired* on the cc
> 6.x line and hand-rolled a `scripts/bundle.sh` generator. **That was
> wrong.** `cyrius distlib` exists and works under the pinned toolchain
> (6.3.x) — it is simply absent from `cyrius --help`'s command list,
> which is what led to the mistaken premise. The `# Generated by: cyrius
> distlib` headers on every sibling's committed bundle were the tell.
> kavach uses the real subcommand; the hand-rolled script was removed
> before this ADR was accepted.

## Decision

Make kavach consumable by adopting the standard first-party library flow,
unchanged from sigil/patra/bhumi.

### 1. `[lib]` profile + `src/lib.cyr` aggregation header

`[lib].modules` in `cyrius.cyml` lists the 41 domain `src/*.cyr` modules
in dependency order (the exact order of `src/main.cyr`'s include block).
It is the **single source of truth** that `cyrius distlib` reads.
`src/lib.cyr` is the human-facing library entry point — the same modules,
same order, as `include` directives — so the surface is legible and
checkable in-tree (`cyrius check --with-deps src/lib.cyr`).

`src/main.cyr` is **excluded** from `[lib]`: it is the in-tree smoke/demo
entry, and bundling it would inline a `main()`/demo and duplicate every
module body into consumers (the `[build].modules`-as-auto-prepend lesson
bhumi and agnosys already recorded). `src/lib.cyr` is also excluded from
the bundle — it is a pure aggregation header, so concatenating it would
leave unresolved `include "src/..."` lines in the flat bundle.

### 2. `cyrius distlib` is the generator; CI gates freshness

`dist/kavach.cyr` and `dist/kavach.deps` are **committed, generated
artifacts**. Regenerate them with `cyrius distlib` after any change to a
`[lib]` module. distlib:

- concatenates `[lib].modules` in order with `# --- <name> ---`
  separators and a `# Generated by: cyrius distlib` provenance header;
- **computes the stdlib sidecar by symbol analysis** — it records only
  the stdlib leaves the bundle's unresolved symbols actually need (for
  kavach: 10 — `string, fmt, alloc, vec, tagged, syscalls, hashmap, str,
  net, process`), which the consumer's `cyrius deps` supplies. This is
  strictly better than enumerating `[deps].stdlib` by hand;
- is **deterministic** (byte-identical on repeated runs).

Freshness is enforced in CI (`.github/workflows/ci.yml`, "Verify dist
bundle fresh"): run `cyrius distlib`, then `git diff --quiet dist/…` —
a stale committed bundle fails the build. This is the same gate sigil and
bhumi use. `scripts/version-bump.sh` also re-runs distlib so a version
bump restamps the bundle header.

### 3. Consumer stdlib contract (the transitive closure)

`cyrius distlib` prints *"stdlib is supplied by the consumer's `[deps]`
stdlib list"* — the Cyrius model is that the **consumer declares stdlib**,
and the `dist/kavach.deps` sidecar records only kavach's **direct** leaves
(10: `string, fmt, alloc, vec, tagged, syscalls, hashmap, str, net,
process`). kavach is the first sibling whose bundle pulls a **transitive
git-dep** (sigil) plus stdlib-heavy paths (the credential-HTTP proxy uses
sandhi → tls), and distlib's per-bundle symbol analysis cannot see those
needs — they live in sigil's/sandhi's own surfaces, not kavach's bundle.

**Consequence (verified):** a consumer that declares only a minimal
`[deps].stdlib` fails to *link* — undefined `thread_local_*` (sigil's
`crypto_scratch`, which backs the audit-chain HMAC), `sandhi_server_*`
(credential proxy), and `TLS_BACKEND_LIBSSL` (sandhi's TLS). So a kavach
consumer **must declare kavach's transitive stdlib** — exactly the pattern
kavach itself follows for sigil (the opt-in `ct`/`keccak`/`thread`/
`thread_local`; see CLAUDE.md's pin-move hazards). Curating a
minimal subset is fragile — the transitive needs cascade (declaring
`sandhi` then demands `tls`, then `async`/`fdlopen`, …) — so **mirror
kavach's `[deps].stdlib`** (the verified set is that list minus the
test-only `args`/`assert`/`bench`). This contract is documented in the
README's "Consume kavach as a library" section. A fuller sidecar *would* make consumption
zero-config, but distlib (correctly, per its design) emits only the direct
leaves, and the CI freshness gate enforces distlib's output — so the
declare-in-consumer contract is the ecosystem-consistent answer.

### 4. Symbol-overlap posture (three clashes: three resolved, one partly)

**Duplicate functions — the `err_*` third is resolved as of v3.11.13.**
kavach and sigil each internalized an `sys_error.cyr` / `sys_util.cyr` in the
agnosys→agnodrm decomposition, so consuming kavach re-emits the `duplicate fn`
(`last definition wins`) warnings kavach's **own** program build already emits.

⚠ **This section previously called that "benign", and for the `err_*` third
that was the wrong call.** The two copies were byte-identical forks — same
kind values, same packing, same `syserr_print` arms — so nothing misbehaved,
which is precisely why fourteen silent collisions survived the whole 3.x line.
But last-def-wins gave *no* mechanism to keep them identical: either side could
have diverged and changed a consumer's error classification with no build
error. sigil namespaced its copies `sigil_err_*` at 3.12.8 and kavach namespaced
its own `kavach_err_*` at v3.11.13; that third no longer overlaps. See
CHANGELOG 3.11.13.

**Still overlapping**, and still resolved only by source order: `syserr_*`
and the `agnosys_*` helpers (vs sigil), plus `path_exists` (vs ai-hwaccel)
and `attestation_result_new` (vs sigil) — 20 warnings on a kavach build, down
from 34. Compatible in practice today, but not *structurally* safe, and
tracked for the same `<crate>_` treatment.

**Resolved — former `ERR_UNKNOWN` value collision (consumer-only).**
sakshi (pulled transitively via sigil for tracing) mints a generic
`ERR_UNKNOWN = 1`; kavach's `SysErrorKind` originally defined a bare
`ERR_UNKNOWN = 7` (alongside `ERR_SYSCALL_FAILED = 1`). Because Cyrius
hoists enum members to global constants under "last definition wins", a
consumer pulling both surfaces got an order-dependent `ERR_UNKNOWN`: under
the pin that verified this ADR the compiler emitted `duplicate symbol
'ERR_UNKNOWN' redefined with conflicting value` and kavach's resolved to
sakshi's `1`; under cc 6.3.35 the same clash resolves *silently* to
whichever definition lands last (reproduced: a two-enum probe printed
`ERR_UNKNOWN resolves to 1`). Either way a consumer could not reliably
distinguish kavach's `ERR_UNKNOWN` from its `ERR_SYSCALL_FAILED = 1`.
kavach's **own** build never saw this (sakshi is not in its auto-include
scope) and its internal classification always round-tripped — so the
defect was consumer-only and latent.

**Fix (this release).** kavach's `SysErrorKind` members are namespaced
`KAVACH_ERR_*` (`KAVACH_ERR_UNKNOWN = 7`, `KAVACH_ERR_SYSCALL_FAILED = 1`,
…), so no kavach error kind shares a name with any dep's generic `ERR_*`.
The change is confined to `src/sys_error.cyr` — the enum, the
`err_*`/`syserr_*` constructors, and the `syserr_print` match arms;
callers reach error kinds only through the constructor/accessor functions
(`err_unknown()`, `syserr_kind()`, …), whose names are unchanged, so no
other `src/` module or consumer call site moves. Behavior is identical
(413 assertions green; create-then-read classification still round-trips),
`dist/kavach.cyr` was regenerated, and a consumer probe confirms
`KAVACH_ERR_UNKNOWN` (7) and sakshi's `ERR_UNKNOWN` (1) now coexist as
distinct values. The **crate-name** prefix (`KAVACH_ERR_*`, not an ad-hoc
abbreviation like `KV*`) is deliberate: repo names are already globally
unique across the first-party tree, so the same `<CRATE>_ERR_*` convention
generalizes tree-wide without the prefixes themselves colliding — sakshi /
sigil adopting it is optional future hygiene, not required for kavach's
consumers.

> **Superseded in part — v3.11.13.** The sentence above ("callers reach error
> kinds only through the constructor/accessor functions … whose names are
> unchanged") was accurate for the release that made the *enum* change, but no
> longer describes the surface. sigil 3.12.8 namespaced its own error
> constructors `err_*` → `sigil_err_*`; sigil and kavach both inherit that file
> from agnosys, so kavach's bare `err_*` had been colliding with sigil's under
> last-def-wins the whole time. kavach namespaced its own to `kavach_err_*` at
> v3.11.13. The `<CRATE>_ERR_*` convention this ADR called "optional future
> hygiene" for other crates turned out to be the thing that resolved it — sigil
> adopted it independently. The `syserr_*` accessors named here are still
> unchanged. See CHANGELOG 3.11.13.

**Resolved — the `KavachError` enum, proactively (this release).** The
separate `KavachError` enum in `src/error.cyr` minted the same class of bare
generic members — `OK`, `TIMEOUT`, `IO_ERROR`, `OTHER` (plus kavach-specific
ones). This ADR's earlier draft left it as "a candidate … if a consumer ever
surfaces a clash." That candidacy was discharged by **verifying the latent
hazard directly** rather than waiting: a two-enum consumer probe under the
pinned line's cc 6.3.35 — `include "dist/kavach.cyr"` plus a dep minting a
generic `OK`/`TIMEOUT`/`IO_ERROR`/`OTHER` — reproduced a **silent** last-def-wins
collision. Two findings made the fix non-optional:

1. **Qualified access does not protect.** Unlike `SysErrorKind` (whose own
   code already used bare members), `KavachError`'s call sites used
   `KavachError.OK` qualified access — but under cc 6.3.35 that is only sugar
   for the hoisted global, so with a later dep's `OK = 100` the probe had
   `KavachError.OK` resolve to **100**, not `0`. kavach's own success/error
   contract would silently shift in a consumer.
2. **The pollution is bidirectional.** With the dep declared first and
   kavach's bundle last, the probe had the **dep's** `OK`/`TIMEOUT`/
   `IO_ERROR`/`OTHER` overwritten to kavach's `0`/`4`/`9`/`10` — kavach was
   corrupting a well-behaved dep, not merely being corrupted.

**Fix.** `KavachError`'s members are namespaced `KAVACH_ERR_*`
(`KAVACH_ERR_OK = 0`, `KAVACH_ERR_TIMEOUT = 4`, `KAVACH_ERR_IO_ERROR = 9`, …),
and every call site — `src/error.cyr` (`kavach_err_name`), `src/lifecycle.cyr`,
`src/sandbox_exec.cyr`, `src/audit.cyr`, `src/backend_dispatch.cyr`,
`src/quarantine.cyr`, and `tests/kavach.tcyr` — uses the bare prefixed name,
matching the `SysErrorKind` convention (bare `KAVACH_ERR_*`, since qualified
access buys no isolation). The prefixed names are disjoint from
`SysErrorKind`'s (`KAVACH_ERR_IO_ERROR` vs `KAVACH_ERR_IO`), so the two enums
coexist. Values, ordering, and `kavach_err_name` output are identical (413
assertions green; `cyrius build src/main.cyr` clean), `dist/kavach.cyr` was
regenerated, and the post-fix probe confirms `KAVACH_ERR_*` (0/4/9/10) and a
foreign dep's generic `OK`/`TIMEOUT`/`IO_ERROR`/`OTHER` (100/200/300/400) now
coexist as distinct values in either include order. With both `SysErrorKind`
and `KavachError` namespaced, kavach's bundle no longer mints **any** bare
generic error constant into a consumer's global namespace.

## Consequences

- **mehman's M1 is unblocked.** The sandbox host becomes mechanical:
  `[deps.kavach] modules = ["dist/kavach.cyr"]` **plus kavach's transitive
  stdlib in the consumer's `[deps].stdlib`** (§3), `cyrius deps`, `include
  "lib/kavach.cyr"`, call the surface. Verified end-to-end: a consumer
  declaring that stdlib set builds and runs the full M1 flow
  (`kavach_init` → … → `sandbox_destroy`) to exit 0.
- **`dist/kavach.cyr` is a committed, regenerated artifact.** It must be
  refreshed with `cyrius distlib` whenever a `[lib]` module changes; the
  CI freshness gate catches a stale bundle.
- **No bespoke tooling.** kavach carries no hand-rolled bundle script —
  the toolchain's `cyrius distlib` is the generator, exactly as across the
  rest of the first-party tree. If distlib grows a `--check` mode
  upstream, the CI gate can swap to it.
- **Consumers inherit kavach's weight**: the ~13 MB static scan tables and
  the benign duplicate-fn warnings. Acceptable — kavach is a security
  engine; a consumer that wants only a slice can revisit if the
  scan-table cost bites (`CYRIUS_DCE=1` drops the unreachable surface at
  build time).
- **No runtime change.** Purely additive packaging; the assertion suite
  and benchmarks are unchanged by construction.

## Amendment — profiles, and the v3.12.6 contract (2026-09-24)

**A second surface: `[lib.confine]` (v3.12.3).** Some consumers need
kavach's process confinement (namespaces, seccomp, Landlock, cgroups, the
runtime guard, the process backend) without the rest of the engine: no
exotic backends, scanners, credential proxy, attestation or audit chain.
thoth asked for it; the full fold pushes thoth's expanded source past the
cyrius preprocessor's 8 MB ceiling and duplicates seams thoth already
consumes (libro's audit chain, t-ron's scanners). The profile folds to
`dist/kavach-confine.cyr` from one module list in `cyrius.cyml`, the same
arrangement as sit's `[lib.read]` and sankoch's `[lib.zlib]`. `src/lib.cyr`
mirrors only `[lib]`.

**Generation covers every profile.** Plain `cyrius distlib` folds `[lib]`
only, so the confine bundle kept its 3.12.3 content through 3.12.5, after
the 6.6.0 value-form migration had changed five of its modules, and would
not compile for a consumer. The generator is now `cyrius distlib --all`, in
`scripts/version-bump.sh` and in the CI freshness gate, and the gate fails
on any change under `dist/`. distlib also has a `--check` mode now, which
reports STALE per bundle without writing.

**§3's stdlib set, re-verified.** The minimal set listed in the README had
fallen behind kavach's `[deps].stdlib`: without `sakshi` a consumer's build
refuses to emit a binary. Corrected at v3.12.6 (`atomic`, `math` and
`sakshi` added) and re-checked end to end on cyrius 6.6.6 through a real
`[deps.kavach]` dependency. A consumer's **sigil** comes from its own
toolchain snapshot: `tls` → `tls_native` includes `lib/sigil.cyr`, and
`cyrius deps` (6.5.39+) will not let a `[deps.sigil]` artifact replace a
stdlib leaf.

## Amendment — the rest of §4, closed, and gated (v3.12.9, 2026-09-25)

§4 left three families "still overlapping, and still resolved only by source
order": the `syserr_*` accessors, the `agnosys_*` helpers, and
`attestation_result_new`, all shared with sigil (and, for `syserr_*` /
`result_print_err` / `is_syscall_err` / `wrap_syscall`, with agnodrm). At
3.12.9 each took the crate prefix this ADR set, or was removed:

- `syserr_*` → `kavach_syserr_*`; `result_print_err` → `kavach_result_print_err`;
  `attestation_result_new` → `kavach_attestation_result_new`;
  `agnosys_json_emit_cstr_or_null` → `kavach_json_emit_cstr_or_null`.
- Removed as unused, in kavach and in every consumer: six `agnosys_*` helpers
  (one of them exec'd by path through the stdlib's `exec_vec`),
  `is_syscall_err`, and `wrap_syscall`.

The same release found the class this section's `KavachError` finding
predicted, live. `InjectionMethod.STDIN` (2) resolved to the stdlib's
`var STDIN = 0` in a consumer, so a stdin secret matched the env-var branch
(filed from agnosai; now archived). Its members are `KAVACH_INJECT_*`, and
`AttestationTrust`'s generic `CONTRAINDICATED` / `WARNING` / `NONE` /
`AFFIRMING` are `KAVACH_TRUST_*`: `attestation_is_acceptable` compares them
numerically, so a foreign `WARNING` could have passed an `AFFIRMING` bar.
kavach's `struct AuditEntry` is `KavachAuditEntry`, because stiva, a consumer,
has its own `AuditEntry` with a different layout and both generated
`AuditEntry_timestamp`.

**Gated.** Fixing instances one at a time leaves the next one live, so
`scripts/check-symbols.py` now runs in CI. It fails on any name kavach defines
twice, any `fn` or struct accessor it shares with `lib/`, and any constant it
shares with `lib/` at a different value. On the 3.12.8 tree it reports exactly
the 20 names above; on 3.12.9 it reports none. Constants shared at equal values
(the 29 errno numbers) are listed, not failed. Its `--tree` mode also lists
names shared with sibling first-party bundles, which no single repo's CI can
see. Those still include generic public names (`policy_new` with shakti;
`finding_new`, `scan_result_new` and `severity_name` with phylax; `which_exists`
with nous; `audit_chain_len` with t-ron). None of those repos is co-resident
with kavach in any consumer today, and renaming public API is a breaking change,
so they are on the roadmap rather than in a patch release.
